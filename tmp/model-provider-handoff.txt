2. USER’S CENTRAL GOALS AND PREFERENCES
======================================================================

The project is an autonomous generative-art installation viewed across four physical monitors, including the spaces between monitors.

The user wants:
- Artworks that remain engaging for hours.
- Continuous temporal variation.
- Visually striking individual frames.
- Rich textures, colors, detail, and compositions.
- More sophisticated behavior, rather than merely adding decorative objects.
- Good performance on a laptop browser with integrated graphics.
- Autonomous gameplay only; no player-controlled gameplay for now.
- Procedural variation in actors, items, structures, terrain, and backgrounds.
- Frontend-only deployment where practical.
- GitHub Pages hosting through GitHub Actions.
- Simulation of monitor delay, refresh differences, jitter, and scanout effects, because professional frame-synchronized GPU hardware may not be used.

Important reactions and corrections:
- The user found Chemical Garden initially broken: it collapsed quickly and preset selection did not work properly. Those problems were addressed in earlier releases.
- The user repeatedly emphasized that simulations must not degenerate into static or visually dull states.
- The user criticized an actual eight-hour wall-clock test being used as if it should be required for every artwork.
- The agreed testing approach is fast regressions and accelerated runs of the actual simulations, with occasional multi-hour qualification for shared runtime or installation hardware changes.
- Do not start an overnight soak for every new artwork.
- The user explicitly prioritized improving the artworks over building exhibition/installation-management features.
- A proposal for curated shows, transitions, kiosk presentation, etc. was deferred in favor of artwork quality.
- They considered the original platformer and murmuration too simplistic.
- For the new terrarium they chose:
  - A living world with interacting inhabitants.
  - Detailed pixel art.
  - A slowly roaming panorama.
- For Life they chose:
  - Directed ecology while retaining Conway’s cell rules.
  - An unassisted option.
- They asked to preserve the original terrarium and add a new variant.

Working relationship:
- The user commonly asks for a plan, approves it, then asks for implementation or says “Continue.”
- Carry approved implementation through testing and deployment instead of stopping after a partial implementation.
- Give truthful status updates and distinguish completed validation from intended targets.
- Do not claim that motion metrics prove artistic quality.
- Do not claim hardware performance that has not actually been measured.

5. PHYSICAL SPACE AND DISPLAY TIMING
======================================================================

The app models four panels as windows into one shared world.

Panel properties include:
- Position in millimeters.
- Active image width and height.
- Bezel.
- Rotation.
- Timing settings.

Default active panel dimensions are approximately:
  531 × 299 mm
with 6 mm bezels and configurable gaps/layouts.

Layouts include:
- Grid.
- Staggered.
- Cascade.

Important invariant:
Objects continue through physical gaps. Each panel must not run its own independent simulation or camera.

For stateful scenes:
- World bounds are captured from the layout when starting the scene.
- Moving panels changes the windows into the world.
- It does not resize/reseed the simulation.

Timing experiments include:
- Delay.
- Refresh frequency.
- Refresh phase.
- Jitter.
- Drift for procedural scenes.
- No scanout, top-down scanout, or bottom-up scanout.

Current validation permits roughly:
- Delay: 0–500 ms.
- Refresh: 24–144 Hz.
- Phase: 0–50 ms.
- Jitter: 0–30 ms.
- Drift: ±200 ppm.

Timing presets include aligned, independent, mixed, and exaggerated configurations.

The timing model selects historical states/images and can choose current versus previous samples by scanout row.

It is a simulation of display synchronization issues. It does not provide actual HDMI frame lock or professional GPU synchronization.

There are separate notions of:
- Fixed simulation ticks.
- Scene/playback time.
- Physical presentation time.

Simulation:
- 60 Hz fixed tick.
- Per-frame catch-up is capped.
- Playback speed changes future clock advancement, not the interpretation of all past time.
- Physical presentation time remains based on real elapsed milliseconds while slow-host simulation catch-up is bounded.
- Hidden tabs and paused playback freeze advancement/monitoring.
- Stateful-scene clock drift is disabled.

Current registered scene version:

Version-1 projects are migrated through existing normalization logic.

Persistence:
- Last project and gallery in IndexedDB.
- Legacy localStorage records are migrated without deleting the old keys.
- JSON import/export.
- Gallery entries include local thumbnails.
- Background persistence approximately once per minute.
- Edits trigger debounced persistence.
- JSON import limit: 16 MB.
- Browser storage is local, not cross-device synchronization.

Replay:
- Simulation parameter edits are recorded by tick.
- Health-driven interventions are recorded.
- Checkpoints include the active parameters.
- Seeking restores a checkpoint or initial recipe and replays events.
- Replays run asynchronously in yielding batches and can be cancelled.
- The clock pauses during pending seeks.

Bounded event history:
- After 2,048 recorded edits/interventions, prior history is summarized in an exact base checkpoint.
- replayFloor records the earliest remaining replay time.
- UI controls reflect that floor.

Determinism:
- Exact CPU replay is tested within the same runtime.
- GPU replay is tested within the same browser/device.
- Do not promise cross-device bitwise identity, especially for floating-point reaction-diffusion.

Canonical portable checkpoint:
  Snapshot {
    tick: number,
    data: number[],
    extra?: object
  }

Do not export compact display history as if it were an authoritative checkpoint.

7. NEW RENDERING ARCHITECTURE AND PERFORMANCE WORK
======================================================================

The old entity path had substantial avoidable work:
- Full simulation snapshots during each panel draw.
- Live-state restoration to paint historical frames.
- Repeated Canvas2D-to-WebGL image transfer.
- Texture allocation churn.
- Preparing previous frames even when scanout did not use them.

The initial short software-renderer profile showed:
- About 775–930 snapshot calls per five-second sample.
- Canvas uploads occupying about 2–3.7 seconds of those samples.
- Slime spending about a second creating full snapshots.

The new architecture separates:
1. Authoritative simulation state.
2. Compact display history.
3. Portable save/replay checkpoints.

Key interfaces:
- Simulation.captureFrame(previous?)
- Scene.createRenderer(gl)
- SceneRenderer.render(frame, appearance, width, height)
- SceneRenderer.dispose()

RenderFrame contains:
- tick.
- Float32Array data.
- Parameters.
- Optional visual metadata.

Important:
- Simulation precision remains unchanged.
- Float32 conversion is for presentation history only.
- Native rendering consumes read-only frames.
- It does not restore or mutate the live simulation.
- Render buffers are reused.

The runtime prepares all requested panel source times before drawing:
- Each distinct source image is rendered once and reused.
- Previous images are requested only when scanout needs them.
- Aligned views normally use two reusable image textures.
- Delayed/mixed views expand the working cache as needed.
- Textures are reused after the cache fills.
- Cached images are invalidated when presentation scale or appearance changes.

Budgets:
- At most 192 entity render frames.
- Default numeric entity history budget: 24 MiB.
- Slime numeric history budget: 32 MiB.
- Eight authoritative checkpoints.
- GPU grid history: 96 MiB budget, at most 192 samples.
- Entity image cache: at most 64 images and 64 MiB pixel payload.
- Atlas resources, working vertex buffers, JavaScript object overhead, and driver memory are additional.

Runtime.states remains available as a compatibility/diagnostic view:
- Native scenes expose renderStates.
- Legacy Canvas scenes expose entityStates.

Native artwork renderer:
  engine/gpu-art.ts

It includes:
- Reusable GPU batches for geometry/sprites.
- Instanced particle ribbons on accelerated drivers.
- Expanded triangle fallback on CPU/software rasterizers.
- Direct Slime field shading.
- Batched flock geometry.

Software-driver selection:
- Detects renderer strings such as SwiftShader, llvmpipe, or software.
- Small-instance dispatch was slower on the CPU rasterizer, so Rivers uses the expanded batch there.
- Both accelerated instancing APIs are explicitly exercised by tests.

Important GL implementation lessons:
- Renderers share a context and must restore/rebind relevant GL state.
- Grid and renderers own their own quad buffers.
- Rebind compositor program, framebuffer, viewport, textures, and attributes after offscreen rendering.
- Reset instancing divisors and disable extra vertex attributes.
- Bind a safe white texture for untextured batches; a declared sampler can cause framebuffer feedback even when a shader branch does not sample it.
- Appearance richness uses current appearance parameters rather than stale historical simulation parameters.

Original Platformer Terrarium retains its Canvas renderer.

8. ADAPTIVE PRESENTATION QUALITY
======================================================================

Preview quality affects presentation, not simulation rules or population.

Modes:
- Auto.
- Economy: 0.75.
- Balanced: 1.
- High: 2.

Auto:
- Initial scale: 1.
- Warmup: two seconds.
- Evaluates active frame intervals in one-second windows.
- After two windows below 50 FPS, lowers scale by 0.125.
- After twelve windows above 58 FPS, raises scale by 0.125.
- Auto range: 0.5–1.5.
- Pauses, hidden tabs, replay, and long observation gaps reset observation windows while retaining scale.

This release changed the thresholds from the older 28/52 FPS policy to favor smoother motion sooner.

It does not change:
- Population.
- Simulation resolution.
- Physics.
- Playback speed.
- Physical display timing.

Terrarium Worlds keeps its 960×600 logical pixel-art source resolution. The compositor still follows preview quality.

Quality is a view setting, not part of the saved artwork recipe.

- Bloom fields.

Monitoring:
- Samples actual cellular state twice per simulation second.
- Divides the field into twelve regions.
- Tracks density/change and recurring regional hashes.
- Keeps up to 32 recent hash observations.
- Distinguishes broad evolving activity from sparse survivors or repetitive local oscillation.
- Cosmetic shader animation is not counted as cellular activity.

Renewal:
- Approximately every four to eight simulation seconds at default variation.
- Earlier intervention for quiet fields.
- Up to four patches per event.
- Combined renewed footprint at most ten percent of the field.
- Locations rotate rather than repeatedly targeting one spot.
- Existing structures outside patches survive.

Presentation:
- Birth highlights.
- Cell-age differentiation.
- Fading generation trails.
- Mosaic/material detail.
- Appearance does not feed back into Conway physics.

Compatibility:
- Hidden ecologyVersion is 2 for new recipes.
- Imported older recipes receive ecologyVersion 1, including initial/checkpoint/event parameter normalization.
- Old recipes retain their prior evolution behavior until an explicit restart or preset selection.
- Selecting a new Life preset or clicking “Restart artwork” enables the new ecology.
- This instruction is important for an existing user opening an old saved Life project.

Director checkpoint state includes:
- Version.
- Next deadline.
- Event serial.
- Quiet budget.
- Previous binary field.
- Recent regional hashes.
- Seeded/changed regional timestamps.

Validation:
- CPU reference generation agrees with the GPU.
- Standard pattern counts/periods/displacement are tested.
- Blank, still-life, and oscillator fields receive distributed renewal.
- Unassisted mode stays untouched.
- Save/replay includes all director decision memory.

Latest long GPU checks:
- All three presets completed thirty simulated minutes.
- Their reported regional coverage remained distributed throughout the checked runs.
- The reported maximum quiet budget was zero in those cases.
- This is evidence for the tested presets/seed, not a mathematical guarantee for arbitrary settings.
- The browser stress script currently uses the app’s seed and does not record it in its result, so improve seed recording if reproducibility across dates becomes important.

16. NEW TERRARIUM WORLDS
======================================================================

Scene ID:
  terrarium-worlds

Core files:
- engine/terrarium-gen.ts
- engine/terrarium.ts
- engine/terrarium-atlas.ts
- engine/terrarium-renderer.ts

It is a separate artwork, not a replacement for platformer.

Visual direction:
- Detailed procedural pixel art.
- Original pixel templates.
- Rich scenery and many simultaneous inhabitants.
- One slowly roaming panoramic camera.

Logical source:
  960 × 600 pixels

Sampling:
  Nearest-neighbor, pixel-aligned presentation.

World generation:
- Nine active chunks.
- Each chunk is 320 pixels wide.
- Three traversable levels.
- Nine navigation nodes per chunk.
- Six placement/height motifs combined with four biome grammars.
- Generated reachable skeleton first, decoration second.
- Chunks ahead are prepared.
- Distant chunks behind the camera are retired.
- Modified retired chunks are not revisited; the camera progresses forward.

Four starting biome presets:
1. Canopy settlements.
   Narrow boughs, hanging routes, villages, fruit and pollination.

2. Fungal caverns.
   Broader stone shelves, tunnels, luminous growth, cave architecture.

3. Rusted aqueducts.
   Arches, cargo lifts, machinery, salvage, waterwheels.

4. Tidal ruins.
   Islands, ferries, water, terraces, wetland structures.

Biomes change geometry, traversal, architecture, vegetation, resources, and background shapes, not only colors.

Population presets:
  48 / 72 / 128

Default 72-actor role distribution:
- 6 explorers.
- 8 haulers.
- 8 builders.
- 22 grazers.
- 24 pollinators.
- 4 hunters/scavengers.

Behavior:
- Explorers visit and activate landmarks.
- Haulers collect renewable materials and deliver stock.
- Builders consume stock to repair structures/routes.
- Grazers forage and distribute seeds.
- Pollinators travel between flowers and boost growth.
- Hunters create pursuits and grazer flight.
- Hunger can send humanoid inhabitants to food.
- Low energy introduces rest.
- Actors age and are replaced outside the view.
- Obsolete routes are replanned.
- Renewable resources and bounded arrivals prevent extinction.

Important interaction chains:
- Pollination → fruit/growth → feeding → seed dispersal → growth.
- Material gathering → transport → stock → repair → usable routes.
- Weather/blooms → resource changes → movement/migration.
- Exploration → remembered discovery → illuminated repaired landmark.

The last published fix connected discovery state to visible landmark lighting.

Navigation:
- Bounded graph routes.
- Walking/jumping/climbing/lifts/ferries.
- Damaged bridges can affect route availability.
- Maximum route length is bounded.
- At most four actor goal-planning operations per simulation tick.
- Work is staggered rather than replanning all actors continuously.

Movement is authored autonomous traversal over a generated navigation graph, including interpolated jump arcs. It is not arbitrary-terrain game AI, reinforcement learning, or a full general collision/physics engine.

Resources/environment:
- Resource growth updates at one-second intervals.
- Structures can degrade.
- Delivered stock is consumed by repairs.
- An event director introduces local maintenance, blooms, migrations, and rediscoveries approximately every 18–30 seconds.
- Weather/day lighting vary over time.

Camera:

17. SHARED EVOLUTION AND RECOVERY
======================================================================

engine/evolution.ts supplies:
- Deterministic scheduled actions.
- Compact activity monitoring.
- Escalating recovery.
- Validation for schedule/action metadata.

Shared watchdog:
- Samples compact simulation activity.
- Keeps a small recent observation window.
- Detects low contrast/change or invalid state.
- Empty states receive early help.
- Other quiet states escalate more slowly.
- Numerical failure can request immediate strong recovery.
- Pause/hidden/replay do not drive recovery.
- Health interventions are recorded for replay.

There is also a presentation fallback layer during recovery.

Important:
Do not confuse cosmetic fallback animation with a healthy simulation.
Life now has its own state-based regional director in addition to the general watchdog.

Analytic scenes such as Julia, Interference, and Contours do not have populations that can become extinct.
